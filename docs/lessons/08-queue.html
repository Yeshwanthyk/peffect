Queue: who owns the next job?

A bounded Queue decouples producers from workers while limiting buffered input. A producer that cannot fit its next message waits. Removing a message transfers ownership to the consumer; finishing that consumer’s later work is an application responsibility.

Workers consume FIFO.
→ end / fail / interrupt →
ClosingReject new input.

DoneNotify takers and awaiters.
Preserve first terminal outcome.

shutdown takes Open or Closing directly to Done, discards buffered jobs and returns unadmitted suffixes to producers. It preserves a Closing queue’s original terminal cause.

inbox = yield from Queue[Job, Done | SourceError].bounded(2)
producer = yield from fork_scoped(
    inbox.into(send_jobs(inbox)), start_immediately=True
)
workers = ...  # fork_scoped workers handle pull.catch_done

yield from producer.join()
yield from inbox.await_()   # no input remains in Queue
for worker in workers:
    yield from worker.join()  # processing removed jobs also finished

into publishes the producer’s Exit. It ends on success, fails on failure, and never enqueues the producer’s return value. Its producer remains interruptible; terminal publication runs masked.

Zero capacity is rendezvous: a read can consume one pending producer message. Waiting takers can provide transient handoff slots. Sliding at zero discards input without takers. peek only sees buffered messages; it does not reserve a pending rendezvous offer.

Batch reads are capacity-aware

take_n(5) on a capacity-two Queue can return two messages. On Closing it can return a short remainder. take_all waits for at least one; clear and poll do not wait. Counts floor fractions and treat NaN/nonpositive values as zero; a completed Queue still reports its terminal outcome before considering zero bounds.

Capacities deliberately follow the pinned vendor’s raw numeric behavior. Use nonnegative integers or unbounded in applications. Fractional, negative and NaN inputs have compatibility characterizations, including vendor quirks; they are outside the normal bounded-capacity guarantee.

Cancellation and completion

A message removed by a receive reaches the first accepting continuation in that same operation, even when resuming a producer interrupts the consumer synchronously. That guarantee ends there: later processing, finalizers and effects can fail or be interrupted. There is no rollback or automatic requeue.

Cancelling a parked producer withdraws only its unadmitted suffix; already admitted messages remain. Cancelling a taker removes its own registration. A scheduled wake asks a taker to retry—it does not reserve a particular message.

Done is normal completion in the typed error channel. take and peek retain it; clear, collect and await_ exclude it while preserving real failures merged with it. poll returns None for empty or terminal; Some(None) still represents an actual None message. Canonical payload unions use Done[X | Y]; Pyright can retain a completion member when inferring exclusion from Done[X] | Done[Y].

Scheduling and capabilities

Queue captures its creator’s dispatcher. Several offers share one queued taker release. flush wakes ready takers synchronously and leaves the scheduled task coalesced; it neither drains nor completes the Queue.

Queue[A, E] is invariant. The same object’s as_enqueue() view is contravariant in both A and E; as_dequeue() is covariant. Capability views restrict methods statically, not by copying the Queue.

The example provides a processor service, records typed job rejection, uses readiness gates to observe genuine backpressure, drains a scoped worker pool, interrupts blocked processing, and drains an admitted job before a typed producer failure. The processor resource closes after worker scopes.
