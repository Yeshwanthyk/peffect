# Effect v4 Schema core — source-grounded scout notes

Scope: vendored `effect-v4/packages/effect/src` only, read on 2026-11-15. Claims below are **read** from the implementation, not runtime-tested. Source citations use paths relative to `packages/effect/src`.

## 1. Schema and codec types

- The simple public `Schema<T>` interface still centers on the decoded `Type`; in v4 it extends `Top`, whose structural surface includes the AST, encoded type, decoding/encoding service requirements, make-input views, and modifiers. The full 15-parameter `Bottom`/`BottomWithoutNew` protocol tracks decoded `T`, encoded `E`, decode services `RD`, encode services `RE`, AST, rebuild type, constructor input/output, iso view, type parameters, mutability, optionality, and defaults. (`Schema.ts:315-350`, `Schema.ts:777-794`, `Schema.ts:976-979`)
- `Codec<T,E,RD,RE>` is the explicit full codec view, while `Decoder<T,RD>` and `Encoder<E,RE>` preserve only one direction. Generic APIs can use lighter `Constraint*` interfaces, and `revealCodec` recovers erased generic views without runtime work. (`Schema.ts:819-899`, `Schema.ts:1083-1110`, `Schema.ts:1129-1162`)
- Thus the design-relevant v4 shape is `Schema[A]` as a convenient decoded-type facade over a richer codec protocol, not one monolithic three-parameter runtime object. For Python, `Schema[A, I, R]` is a useful ergonomic grouping, but Effect itself distinguishes decoding and encoding environments (`RD` and `RE`). (`Schema.ts:976-979`, `Schema.ts:1083-1088`)
- Version comparison limit: this scoped source does not contain v3's implementation. It does establish `Schema<T>` and several combinators as `@since 3.10.0`, while `Codec<T,E,RD,RE>`, `Decoder`, `Encoder`, and `Top` are annotated `@since 4.0.0`; do not infer a complete v3-to-v4 semantic delta from those annotations alone. (`Schema.ts:976-979`, `Schema.ts:777-818`, `Schema.ts:1083-1106`, `Schema.ts:1129-1134`)

## 2. AST and encoded links

- AST is a tagged union: `Declaration`, primitive/special nodes (`Null`, `Undefined`, `Void`, `Never`, `Unknown`, `Any`, `String`, `Number`, `Boolean`, `BigInt`, `Symbol`, `Literal`, `UniqueSymbol`, `ObjectKeyword`, `Enum`), plus `TemplateLiteral`, `Arrays`, `Objects`, `Union`, and `Suspend`. Common AST metadata is `_tag`, annotations, checks, optional encoding, and context. (`SchemaAST.ts:45-78`, `SchemaAST.ts:685-718`)
- Encoding is explicitly represented on AST nodes, not just held as a wrapper on the Schema value. An `Encoding` is a nonempty chain of `Link { to: AST, transformation }`; each transformation or middleware links the current representation to another AST. `decodeTo` appends a link to the target AST's chain. (`SchemaAST.ts:405-476`, `SchemaAST.ts:4588-4612`)
- The parser compiles links once, then traverses them from the outer encoded side inward for decode; `flip(ast)` swaps direction for encode. Per-link `Transformation` holds decode/encode getters, and `Middleware` can wrap the full optional Effect pipeline. (`internal/schema/interpreter.ts:24-80`, `internal/schema/interpreter.ts:221-253`, `SchemaTransformation.ts:78-120`, `SchemaTransformation.ts:183-218`, `SchemaParser.ts:633-644`)

## 3. Parser, services, and issue trees

- AST nodes provide `getParser`; the interpreter composes node parser + checks + encoding links and memoizes link parsers. Its internal parser type accepts unknown input/options and returns `Effect<unknown, Issue, any>`; `run(ast)` specializes that to typed outputs and service requirements. (`SchemaAST.ts:2829-2845`, `SchemaAST.ts:3707-3720`, `internal/schema/interpreter.ts:131-156`, `SchemaParser.ts:973-1019`)
- The effect APIs preserve typed environment requirements: `decodeUnknownEffect` returns `Effect<Type, Issue, DecodingServices>` and `encodeUnknownEffect` parses `flip(schema.ast)` and returns `Effect<Encoded, Issue, EncodingServices>`. Sync and Promise / Result / Exit / Option helpers are boundary adapters; sync forms can fail at a sync boundary if effects cannot complete synchronously. (`SchemaParser.ts:270-280`, `SchemaParser.ts:633-644`, `SchemaParser.ts:566-573`, `SchemaParser.ts:923-930`)
- Pure getters use a direct synchronous success path; effectful getters return Effects and can fail with an Issue or require services. `Getter` is Option-aware so absent fields can pass through, be omitted, or be materialized without conflating absence with `None`/null values. (`SchemaGetter.ts:135-160`, `SchemaGetter.ts:722-766`)
- Issue is a recursive tagged tree: leaves include invalid type/value and missing/unexpected keys; `Pointer(path, issue)` adds a field/index location; `Composite(ast, nonempty issues)` groups product/check failures; `AnyOf(ast, member issues)` and `OneOf(ast, successful members)` represent union failures; `Encoding(ast, issue)` wraps failures crossing a transformation link. Input is retained only when `reportInput` is enabled. (`SchemaIssue.ts:147-163`, `SchemaIssue.ts:394-438`, `SchemaIssue.ts:581-614`, `SchemaIssue.ts:919-928`, `SchemaIssue.ts:1003-1013`, `SchemaIssue.ts:753-790`, `SchemaIssue.ts:313-370`)
- Object/tuple parsing wraps child failures with `Pointer`, wraps the aggregate in `Composite`, and honors `errors: "all"` to collect children versus first-error behavior. Union matching narrows candidate members by runtime type and literal sentinel fields, then returns `AnyOf` with candidate failures (or an empty issue list when none apply). (`SchemaAST.ts:2530-2551`, `SchemaAST.ts:2577-2603`, `SchemaAST.ts:3020-3055`, `SchemaAST.ts:3102-3107`, `SchemaAST.ts:3531-3673`, `SchemaAST.ts:3788-3805`, `SchemaAST.ts:3918-3940`)

## 4. Transformations and getters

- `Getter<T,E,R>` variants are passthrough, pure present-value transform, pure Option transform, effectful present-value transform, or effectful Option transform. `Transformation<T,E,RD,RE>` pairs a decode getter and reverse encode getter; `flip()` swaps them. Middleware instead intercepts an `Effect<Option<E>,Issue,R>` and is intended for retry/fallback/pipeline-level behavior. (`SchemaGetter.ts:135-160`, `SchemaTransformation.ts:78-120`, `SchemaTransformation.ts:183-218`)
- Custom pure transform: `SchemaTransformation.transform({ decode: e => t, encode: t => e })`. For possible failure, async work, or services, use `transformEffect({ decode: (e, options) => Effect<T,Issue,RD>, encode: (t, options) => Effect<E,Issue,RE> })`. For custom Option semantics, use getter `transformOptional` / `transformOptionalEffect`. (`SchemaTransformation.ts:440-448`, `SchemaTransformation.ts:390-398`, `SchemaGetter.ts:763-767`, `SchemaGetter.ts:800-825`)
- `decodeTo(to, transformation)(from)` makes the decoded side `to.Type` and encoded side `from.Encoded`; it combines services from both schemas and the custom transformation. The custom decode direction maps `From.Type -> To.Encoded`, then the target schema parses that; encode is the inverse route. (`Schema.ts:5640-5660`, `Schema.ts:5671-5745`)

## 5. Checks, refinements, brands, structs, classes, unions

- Checks are AST-attached pure filters or `FilterGroup`s; each filter can return an issue and can abort later checks. `.check(...)` preserves the schema rebuild type. `refine` adds a guard-backed runtime filter and narrows `Type`; `brand` only adds a nominal TypeScript brand and explicitly does not add runtime validation. `fromBrand` additionally applies the brand constructor checks. (`SchemaAST.ts:4108-4118`, `SchemaAST.ts:4183-4243`, `Schema.ts:5243-5247`, `Schema.ts:5292-5298`, `Schema.ts:5324-5362`, `Schema.ts:5383-5393`)
- `Struct(fields)` builds an `Objects` AST from each field AST; its `Type` and `Encoded` are mapped field views, and required/optional/defaulted/mutable metadata is preserved in its type protocol. Runtime object parsing handles declared and index-signature fields, own/inherited-property rules, excess properties, defaults, and configurable concurrency. (`Schema.ts:3450-3507`, `Schema.ts:3571-3606`, `SchemaAST.ts:2829-2885`, `SchemaAST.ts:2911-2925`, `SchemaAST.ts:3020-3107`)
- `Class` wraps a Struct schema as a schema-backed class with validated construction and encode/decode; class transformation constructs trusted instances after field parsing. `TaggedClass` adds a literal `_tag` field; `TaggedError` does the same while creating a yieldable Effect error. (`Schema.ts:17418-17437`, `Schema.ts:17631-17635`, `Schema.ts:17690-17723`, `Schema.ts:17766-17794`, `Schema.ts:17826-17858`, `Schema.ts:17918-17924`, `Schema.ts:17947-17980`)
- `Union(members, { mode })` defaults to `anyOf` (first applicable success); `oneOf` requires exactly one matching member. The parser builds a cached candidate index from runtime type and sentinel fields, so tagged objects can be dispatched efficiently; `toTaggedUnion(tag)` additionally provides discriminant/case/guard/match helpers and rejects duplicate tags. Tagged structs require `_tag` during decode/encode unless using a defaulting/omit helper. (`Schema.ts:5020-5025`, `SchemaAST.ts:3730-3739`, `SchemaAST.ts:3531-3673`, `SchemaAST.ts:3788-3805`, `Schema.ts:6486-6527`, `Schema.ts:6325-6344`)

## 6. Implementation invariants worth preserving

- Keep input representation, decoded representation, and encode direction explicit. Encoding must reverse the chain, swap per-link getters, and swap type-side versus encoding checks; do not model encode as “serialize the decoded model” without carrying its inverse codec. (`SchemaAST.ts:4588-4612`, `SchemaAST.ts:745-754`, `internal/schema/interpreter.ts:221-253`)
- Missing is a dedicated internal sentinel, not `undefined` or `None`; field parsers use it to apply defaults, distinguish absent keys, and omit outputs. A Python port needs a unique sentinel through every nested parse and transform boundary. (`internal/schema/parser.ts:5-34`, `SchemaAST.ts:2538-2551`, `SchemaAST.ts:3246-3265`, `SchemaAST.ts:4578-4585`)
- Type checks/shape parsing still run when `disableChecks` is true; only filters/checks are skipped. Struct field mapping drops checks by default because old check predicates may not apply to a changed shape; preserving them is explicitly unsafe. (`SchemaAST.ts:541-546`, `internal/schema/interpreter.ts:157-210`, `Schema.ts:3538-3545`, `Schema.ts:3564-3567`)
- Composite issue nodes require at least one child; pointers wrap one issue and path, while a zero-applicable union is represented as `AnyOf` with an empty list. Respect those distinct shapes rather than flattening all failures into strings. (`SchemaIssue.ts:581-614`, `SchemaIssue.ts:919-928`, `SchemaAST.ts:3792-3805`)
- Concurrent product parsing can change issue ordering and the first observed failure; union members remain sequential. If Python adds asyncio concurrency, preserve output order and document failure ordering/side effects explicitly. (`SchemaAST.ts:547-560`, `SchemaAST.ts:3061-3099`, `SchemaAST.ts:3681-3687`)

## 7. Python + pydantic boundary

**Recommendation (inferred from the code):** let pydantic-core own ordinary Python input validation/coercion and model construction where its behavior is sufficient; retain an Effect-like Schema layer for the semantics pydantic alone does not express as one typed codec.

A thin `Schema[A, I, R]` over pydantic should add:

1. An explicit pair of directions: decode `I -> A` and encode `A -> I`, with transformations composed in opposite order and separately typed decoding/encoding requirements (`RD`/`RE`). (`Schema.ts:1083-1088`, `Schema.ts:5640-5655`, `SchemaParser.ts:270-280`, `SchemaParser.ts:633-644`)
2. An async/effectful decoder whose requirements are injectable services and whose expected validation failure is a structured issue value; pydantic can do the local shape work, while the schema layer sequences service-dependent checks/transforms around it. (`SchemaGetter.ts:763-767`, `SchemaTransformation.ts:390-398`, `SchemaParser.ts:270-280`)
3. A stable recursive issue model with path pointers, nested composites, union alternatives, and transform context, plus adapters to exceptions/results. A flat pydantic error list may be an input to this conversion but is not the same public failure contract. (`SchemaIssue.ts:147-163`, `SchemaIssue.ts:394-438`, `SchemaIssue.ts:581-614`, `SchemaIssue.ts:919-952`, `SchemaParser.ts:1021-1035`)
4. Missing-vs-null handling, omission/defaults, check disabling, excess-property policy, and discriminated union candidate selection where the Python model needs Effect-compatible behavior. (`internal/schema/parser.ts:5-34`, `SchemaAST.ts:541-598`, `SchemaAST.ts:3020-3055`, `SchemaAST.ts:3531-3673`)

Do not reimplement pydantic's basic parsing engine just to duplicate it. Do not delegate the entire abstraction to pydantic if the goal includes effectful decoding/encoding, typed service requirements, reversible transforms, or Effect-compatible issue trees. The exact adapter boundary remains a design choice for the Python draft; the Effect source establishes the behaviors above, not pydantic's compatibility or performance. (`SchemaParser.ts:270-280`, `SchemaParser.ts:633-644`, `SchemaTransformation.ts:183-218`, `SchemaIssue.ts:147-154`)
