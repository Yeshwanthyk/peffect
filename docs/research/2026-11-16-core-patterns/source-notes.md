## Concrete candidates

1. **Give a suspension a single explicit winner/lifecycle bit, especially across registration-versus-resume phases.**
   - **Source fact:** Effect `internal/effect.ts` at pinned commit, `callbackOptions`/Async implementation around lines 1206–1273: `resumed` is the one-shot winner; `yielded` distinguishes synchronous registration from a parked fiber; cancellation's finalizer marks resumed and aborts. In peffect, `core.py:562–571` defines `Park(done, registering, sync)` and `Async._eval` at `587–606` coordinates immediate resume, park, and cancel; `fiber.py:302–320` repeats `Park.done` arbitration for queued yield.
   - **Recommendation / call site:** Preserve `Park` as the authoritative protocol state at `core.Async._eval` and `Fiber.yield_now`; reason about transition order as a lifecycle rather than distributing flags among callbacks. Review whether the two users truly share all state semantics before merging/generalizing.
   - **Boundary / not to apply:** A lifecycle object is not automatically better than a closure. `Async`'s per-evaluation local park and callbacks are naturally scoped; an object adds value when multiple methods must own/inspect the lifecycle, not merely to avoid closures. Crucially, peffect's cancel effect is pushed only after parking, while upstream has an async finalizer; apparent structural similarity does not prove cancellation parity.

2. **Publish terminal/admission state before invoking user callbacks that can reenter.**
   - **Source fact:** Effect `Queue.ts` at pinned commit, `releaseCapacity` lines 2109 onward and `takeOfferUnsafe` immediately above: buffer/reservation and registry removal occur before producer resume, then capacity/state are re-read because resumed producer can synchronously take, offer, or shut down. `releaseTakers` likewise removes the taker before resume. Peffect's `queue.py:532–551` explicitly follows this ordering in `_release_capacity`; `_take_offer` at `518–530` removes completed entry before resume. `fiber.py:790–813` records failure/terminal before `finish()` interrupts workers, noting interrupts may reenter observers.
   - **Recommendation / call site:** Treat each callback/resume in `Queue._release_capacity`, `_take_offer`, and traversal `record/finish` as an arbitrary synchronous reentry point. Establish invariants (reservation, terminal, membership removal) first; after callback, re-read state before deciding another transition.
   - **Boundary / not to apply:** Do not force a universal “all callbacks last” ordering: some callbacks are explicitly observers of a completed transition, and exceptions have defined defect handling. This does not imply all intermediate mutation is atomic under threads; source here establishes synchronous reentrancy concerns.

3. **Use live ordered waiter membership with cancellation-owned tokens; avoid stale copied snapshots when cancellation can remove a waiter.**
   - **Source fact:** Effect Queue uses `Set` iteration while deleting entries during release (`Queue.ts:1998–2007`, `2109+`); `awaitTake` inserts a taker and returns a cancellation effect that deletes it (`2060–2067`). Peffect implements `_Registry` (`queue.py:200–247`) with ordered tokens/tombstones, explicitly supporting append/delete during callbacks because Python dict iteration forbids mutation; `_await_take` captures a token and returns its removal as cancel action (`495–507`).
   - **Recommendation / call site:** Retain registry iteration semantics as a named invariant at `flush_unsafe`, `_schedule_takers`, and `_release_capacity`; cancellation token ownership should stay attached to registration rather than inferred from a copied waiter list.
   - **Boundary / not to apply:** Python's dict mutation restriction is a language-specific reason for the tombstone registry, not a reason to clone Effect's data structure. A simple snapshot is appropriate where membership is intentionally frozen (e.g. interrupting current losers in `fiber.py:967–969`) and later arrivals must not join that operation.

4. **Split pure transition/admission calculation from effectful publication only where it makes the observable protocol clearer; otherwise preserve a short interleaved loop with revalidation.**
   - **Source fact:** In peffect, `_release_capacity` computes available space from live queue length, admits a producer's entry, removes it, resumes it, then loops; comments say it re-reads state for every offer (`queue.py:532–551`). In `fiber.py`, `pump` combines item admission and worker starts (`750–771`), while `can_start` centralizes admission predicate (`747–749`). Effect Queue's release routine has the same interleaved reserve/remove/resume sequence. These are code facts, not evidence that one decomposition is safer.
   - **Recommendation / call site:** For a proposed queue refactor, first specify a transition result (which entry/message is reserved, new offset, remaining capacity) and identify the linearization point. Keep publication separate only if the plan can still revalidate after each reentrant resume; consider `Queue._release_capacity` and traversal `_run_window.pump` as separate cases rather than imposing one pattern across both.
   - **Boundary / not to apply:** Precomputing a batch of admissions from a stale snapshot is incorrect if resume can consume capacity or close the queue before the next admission. Conversely, extracting a “pure” calculator can be ceremony if it duplicates mutable state or cannot represent callback-induced state changes.

5. **Make outcome/phase unions explicit; distinguish open, closing, and done instead of overloading sentinel values.**
   - **Source fact:** Peffect Queue has `_Active(terminal=None | Failure)` and immutable `_Done(terminal)` (`queue.py:270–282`), and branches accordingly in offer/take/finalize paths. Peffect traversal separately stores `failure: Failure | None` and `cancelled: bool`, with admission derived in `can_start` (`fiber.py:734–749`); code comments explicitly say failure never holds success-as-cancellation sentinel. Python typing docs document user-defined generic types and unions/type parameters: https://docs.python.org/3/library/typing.html#user-defined-generic-types and https://docs.python.org/3/library/typing.html#typing.Union.
   - **Recommendation / call site:** Keep queue lifecycle and traversal terminal/cancellation channels semantically distinct at `Queue._state` and `_run_window`; consider an explicit tagged representation only if it simplifies invariants without obscuring `Failure[E]` typing.
   - **Boundary / not to apply:** Not every pair of booleans needs a class. `cancelled` and `failure` encode independently meaningful events (cancellation versus a failure that should be returned), so collapsing them into one enum or sentinel risks losing cleanup-failure accumulation behavior.

6. **Treat types as boundary contracts, not runtime validation; preserve generic distinctions at callback/registry seams.**
   - **Source fact:** Python typing docs state annotations/type hints are not enforced by the runtime (https://docs.python.org/3/library/typing.html#typing.TYPE_CHECKING and typing intro); generic classes parameterize reusable containers. Locally, `core.py:558–560` defines `Resume` and `Register` aliases, while `queue.py:250–277` types single/batch offers, takers, and active registries separately. `fiber.py:721–729` keeps traversal input/output/error/resource channels distinct in its registration signature.
   - **Recommendation / call site:** Preserve these typed callback boundaries when changing `Async`, `_wait_offer`, `_await_take`, or `_run_window`; where an external/user callback can violate assumptions, keep the runtime error/defect path (e.g. `Fiber.evaluate` catches exceptions at `fiber.py:277–280`) rather than assuming type checking protects it.
   - **Boundary / not to apply:** A type alias or protocol does not establish runtime cancellation safety, single-resume behavior, or exclusion of effects. Do not add casts or widen `Any` merely to make a transition refactor type-check; inspect concrete call sites and checker evidence later.
