### Candidates beyond the named areas

- **Reference-counted keyed resource map (`RcMap`) — strongest overlooked candidate.** Upstream explicitly describes sharing an in-progress or acquired resource by key, tying each caller to its Scope, then releasing at zero references; it also supports idle TTL and capacity limits. This directly extends the app’s existing Layer/resource composition to keyed clients, sessions, or connections. Evidence: [`RcMap.ts`](../../../vendor/effect-v4/packages/effect/src/RcMap.ts#L1) says it is for resource lifecycles, not a general cache; its public `lookup` requires `Scope` and its model carries idle TTL/capacity ([lines 77–84](../../../vendor/effect-v4/packages/effect/src/RcMap.ts#L77)). Source imports include `Cause`, `Clock`, `Context`, `Deferred`, `Duration`, `Effect`, `Exit`, `Fiber`, mutable map, and `Scope` ([lines 17–30](../../../vendor/effect-v4/packages/effect/src/RcMap.ts#L17)). Given the current foundations, the **inferred** smallest useful first slice is keyed acquisition sharing plus per-scope reference tracking and release at zero; defer TTL, capacity, and invalidation until callers demand them. Correctness proof should cover concurrent same-key acquisition, independent scopes, interrupted acquisition/waiters, exactly-once release, and close/invalidate races. State ownership and lifecycle cleanup are the main maintenance risks; avoid broadening into a generic cache.

- **Request batching/resolution — plausible, but conditional on an actual batch data source.** Upstream contract has a resolver delay, batch key, optional pre-check, collection predicate, and `runAll` over a non-empty batch ([`RequestResolver.ts:83–107`](../../../vendor/effect-v4/packages/effect/src/RequestResolver.ts#L83)). The existing observability scout has already traced the internal queueing/cancellation behavior and concluded this is in-flight coalescing, not persistent result caching ([`observability.md:23–27`](../../../docs/scouts/observability.md#L23)). Its inferred minimal dependencies are request completion, fiber interruption, delay/Clock, and per-key in-flight state. High value for batched RPC/DB reads; otherwise defer because it adds a nontrivial lifecycle/state machine absent from the reported app scenarios. Proof targets: batching boundaries, resolver failure or omitted completion, cancellation of one versus all entries, and cleanup of empty batches.

- **Metrics — useful after applications need operational measurements; keep tracing distinct.** Upstream’s `Metric` includes counters, gauges, frequencies, histograms, summaries, update/read, attributes, snapshots, and runtime metrics ([`Metric.ts:1–9,33–49`](../../../vendor/effect-v4/packages/effect/src/Metric.ts#L1)). Its imports show a broad implementation surface, including internal Effect/Metric and Layer, so this is not a tiny primitive ([lines 15–30](../../../vendor/effect-v4/packages/effect/src/Metric.ts#L15)). A narrower first slice could be fiber-safe counter/gauge values plus update/read and a snapshot boundary; defer exporters, runtime instrumentation, histogram/summary aggregation. Prove concurrent updates and isolation between runtimes. The current roadmap already places Logger/Tracer/Metric in tier 8; this is a prioritization observation, not a proposed duplicate lane.

- **Persistence-backed rate limiting — defer as a separate integration/package.** Upstream marks it unstable and defines token consumption/adaptive feedback over a `RateLimiterStore` service ([`persistence/RateLimiter.ts:1–12,52–67`](../../../vendor/effect-v4/packages/effect/src/persistence/RateLimiter.ts#L1)); implementation pulls Config, Schema, Layer, Schedule, and Redis ([lines 14–24](../../../vendor/effect-v4/packages/effect/src/persistence/RateLimiter.ts#L14)). That dependency footprint and cross-process semantics make a Redis-backed port poor foundational scope. If a concrete app needs only local throttling, first determine whether existing Semaphore + Clock suffices; do not present that as equivalent to persistent fixed-window/token-bucket quotas.
